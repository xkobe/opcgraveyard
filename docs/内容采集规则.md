# 一人公司坟场 · 内容采集规则（v1.0）

> 目标：**每天新增 10 条**真实 AI OPC / 独立开发者失败案例，国内外公开报道全量覆盖，快速积累至 **500 条**后正式部署上线，获取 SEO 流量。
> 执行载体：GitHub Actions 定时（cron）自动运行采集脚本；人工仅做质量抽查与最终上线决策。

---

## 一、收录硬门槛（5 条，缺一不可）

| # | 门槛 | 判定方式 |
|---|------|----------|
| 1 | **真实发生** | 必须来自公开报道/官方公告/创始人自述；凡无法定位到原始报道者一律丢弃 |
| 2 | **可溯源** | 每条必须有 ≥1 个真实可点击的来源 URL（媒体文章/官网公告/创始人帖子），禁止凭搜索摘要撰写 |
| 3 | **死因可拆解** | 能拆出"表层→中间→深层"三层机制，且能归入六大死因之一 |
| 4 | **AI / OPC 属性** | 独立开发者 / 一人公司 / 极小团队（≤5人），或失败与 AI 应用/AI 冲击直接相关 |
| 5 | **有教训价值** | 能提炼 ≥3 条可执行避坑清单 |

**明确不收录**：Taskade 等"composites"合成案例；大厂砍产品线（战略收缩而非创业失败）；纯融资暴雷但无产品故事的；无法溯源的单方匿名爆料。

## 二、来源渠道矩阵（每次巡检全量覆盖）

### 中文来源（重点：中国市场案例优先）
- **36氪**（创业复盘/失败专栏）— 固定巡检
- **澎湃新闻**（一人公司/OPC 专题）
- **DoNews / 虎嗅**（创业者实录）
- **人人都是产品经理**（产品经理复盘）
- **知乎 / 即刻**（创始人亲述关停）
- **微信公众号**（OPC/独立开发者社群，如 SoloNest 等）

### 海外来源
- **Failory Newsletter**（倒闭访谈，主力）
- **AI Graveyard / Vibe Coding Graveyard**（AI 工具关停档案，注意区分真实名/化名）
- **Indie Hackers**（独立开发者失败帖）
- **Hacker News**（关停公告帖 + 复盘讨论）
- **TechCrunch / The Information**（融资后关停新闻）
- **Product Hunt**（上线后失败的评论风向）
- **YC / 加速器校友动态**（明星项目关停）

### 沉默死亡主动追踪（`scripts/stale_tracker.py`，2026-11 新增）

前面所有来源有一个共同前提：**得有人先把这件事写成新闻**。但绝大多数一人公司不是这样死的——产品悄悄关站、域名到期不续、创始人默默去找工作，从头到尾没有一篇报道。这类案例在纯新闻采集里覆盖率是 0。

所以单独开一条不依赖新闻的通道：用**时间戳 + 存在性**主动发现。

**双闸门，两个都过才进候选：**

| 闸门 | 判据 | 说明 |
|---|---|---|
| 一 · 时间 | 项目最后一次可观测活动距今 ≥ 12 个月 | 太新的项目可能只是在放假 |
| 二 · 存在性 | 根路径 DNS 返回 NXDOMAIN，或 `https://根域/` 与 `https://www.根域/` **都**返回 404/410 | 只过闸门一的（停更但还活着）不算死 |

**三道质量闸（防噪音）：**

1. **根路径检测**：只用根域重测，不用原始 URL。原 URL 常是 `/blog/xxx` 这类子路径，子页面 404 不代表产品死了（实测 Nanonets 就是活得好好的公司，但那条 Show HN 指向的子页早没了）。
2. **子域不算死**：`demo.` / `docs.` / `blog.` / `status.` 这类子域消失，只要主域还在，一律不判死。
3. **商业性闸门**：域名死了 ≠ 这是个创业项目。Show HN 上绝大多数是周末玩具和玩笑站，它们消失得比商业项目还快，但从来不是"一人公司"。要求当时的讨论里至少命中 2 个付费/商业模式信号（pricing、subscription、customer、revenue…）。不加这一关，案例库会塞满"地图记忆小游戏"。

**当前通道状态（2026-11 实测）：**

| 通道 | 状态 | 说明 |
|---|---|---|
| Hacker News Show HN | ✅ 启用 | 主通道。每次随机扫 2 个月份（12–36 个月前），36 个月 18 天轮完一遍 |
| GitHub 仓库停更 | ⏸ 备用 | 需 `GITHUB_TOKEN`，默认关闭。停更的开源仓库多数是个人工具，噪音比 HN 高一个量级 |
| Indie Hackers | ❌ 不可用 | 全站 403（Cloudflare）；三个子 sitemap 共 105829 个 URL 全是 post，`/product/` 路径数为 0，拿不到产品列表 |

**产出形态**：候选的 `body` 是一份「沉默死亡检测报告」——项目名、HN 讨论链接、存活检测结果、评论摘录，外加一段强约束（材料里没有的融资额/收入/用户数一律写"未披露"，不得推测）。`is_selfpost=True` 且正文远超 120 字，`fetch_all()` 第一轮直接接住，不占抓取名额，也不会去抓那个已经死掉的域名。

```
中文：AI创业失败 / AI公司倒闭 / AI产品关停 / 独立开发者失败 / 一人公司 失败 /
      创业复盘 / 项目暂停 / 注销公司 / 停止服务 / 融资后倒闭
英文：AI startup shutdown / AI product sunset / indie hacker failure /
      startup postmortem / failed AI startup / AI graveyard /
      one person company failure / shut down / discontinued / winding down
```

时效过滤：优先 `freshness ≤ 30 天` 的新报道；存量补录放宽至任意时间。

## 四、采集流程（脚本自动化五步）

```
搜索发现 → URL 初筛 → 正文抓取核实 → LLM 生成案例 → 去重合入
```

1. **搜索发现**：四源并行——Google News RSS（中英关键词）、Hacker News Algolia、中文媒体 RSS、**沉默死亡主动追踪**（`stale_tracker.py`，不依赖新闻，靠时间戳 + 域名存活性发现悄悄关站的项目）。四源交错合并，避免 fetch 阶段只取到单一来源
2. **URL 初筛**：匹配来源白名单；标题含"关停/倒闭/失败/注销/shutdown/sunset/failed"等信号词优先
3. **正文抓取核实**：打开来源页面，提取时间线、金额、创始人、死因细节；**禁止凭摘要写**
4. **LLM 生成**：按 CaseRecord 模板生成完整字段，所有数字/时间必须来自抓取正文
5. **去重合入**：按 slug/name/来源 URL 三重去重，跳过已收录，追加写入 cases.ts

---

## 五、去重机制

- **slug 唯一**：新增前比对 CASES 现有 slug，冲突则改名或丢弃
- **name 相似度查重**：同产品/同创始人只收 1 条，后续变化用状态迁移（dead → pivoted），不新开
- **来源 URL 查重**：同一事件多篇报道只收录 1 条，source 合并列多个媒体
- **已收录清单**：脚本每日从 cases.ts 读取现有 slug/name 作为基线，跨天不重复

## 六、内容质量规范

### 字段模板（CaseRecord，全部必填）
| 字段 | 要求 |
|------|------|
| slug | 小写英文短横线，语义化唯一 |
| name | 墓碑名（真实产品名或"人名·行业"描述名） |
| status | dead / acquired / pivoted 三选一 |
| founderBg / region / industry | 创始人背景、地区、行业 |
| startedAt / closedAt | YYYY 或 YYYY-MM（可核验粒度） |
| lifespanMonths | 整数月数（= closedAt − startedAt，估算时取整） |
| investment / fundingType | 投入金额 + 自筹/融资/混合 |
| deadCause / deadCauseSub | 主因 + 子因（见第七节） |
| source | 来源媒体名 |
| verified | 双源或权威单源为 true；仅创始人自述为 false |
| epitaph | 墓碑摘要：2-3 行，点死因 + 关键数字 |
| motivation | 创业动机：100-200 字 |
| timeline | 3-6 个 {time,event} 节点 |
| breakdown | ≥3 层：表层原因→中间机制→深层机制 |
| lessons | 3-5 条可执行教训 |

### 叙事结构
"墓碑摘要（数字冲击）→ 动机（为什么出发）→ 时间线（怎么死的）→ 三层拆解（为什么会死）→ 教训（怎么避坑）"

### SEO 规范（为流量服务）
- **时效优先**：近 30 天关停案例优先收录，详情页天然带"2026 年 AI 公司倒闭"等时效关键词
- **标题结构**：`案例名 · 细分行业：死因 | 死亡档案 | 一人公司坟场`（已自动继承）
- **关键词密度**：epitaph 与 lessons 自然融入"AI 创业失败/独立开发者/一人公司/死因"等长尾词
- **死因标签**：六大死因作为稳定分类词，聚合页可承接"XX 死因的创业公司"搜索

## 七、死因分类体系（主因 + 子因）

```
获客失败                  个人品牌未建立 / 渠道缺失 / 流量成本失控
需求验证缺失              先做再想 / 伪需求 / 市场被替代
商业模式脆弱              融资来源单一 / 大客户依赖 / 用户多不赚钱 / 回款风险
成本结构失衡              固定支出吞噬 / 算力成本失控 / 库存积压 / 毛利为负
同质化竞争                AI 抹平门槛 / 被通用模型吸收 / 价格战
合规与决策风险            监管处罚 / 数据合规 / 造假曝光 / 一人决策无纠偏
```

- 主因规则：按"最先导致死亡的那一环"归因
- **覆盖均衡策略**：当前分布 商业模式脆弱6 / 同质化4 / 需求验证缺失3 / 合规2 / 获客失败1 / **成本结构失衡0**。采集时优先挑选能补"成本结构失衡"与"获客失败"的案例，保证 500 条时六大类均衡、首页统计不畸形。

## 八、更新节奏与上线门槛

| 阶段 | 动作 |
|------|------|
| 每天 | GitHub Actions cron 触发采集（默认 10 条/天），自动合入 + 提交 |
| 每天 | 主 Agent 抽查当日新增（死因/溯源/格式），异常则修正或回滚 |
| 累计 500 条 | 停止增量扩容，全量静态检查 + 浏览器回归 → 正式部署上线 |

**达标前**：不部署线上（用户明确要求 500 条门槛），本地/预览域持续积累。

## 九、质量红线（脚本内置校验）

- 金额、时间、人名**必须来自来源原文**，LLM 不得臆造；无法核验的细节留空或标注"未披露"
- `verified: true` 需 ≥2 独立来源或 1 个权威来源；只有创始人单方自述 → false
- 每条案例必须**带来源 URL**（写入 source 字段）；无 URL 的生成结果一律丢弃
- 每日脚本自检：TS 语法可解析、必填字段齐全、slug 无重复、死因在六大类枚举内

## 十、运行载体（GitHub Actions）

- **定时**：每天 1 次 cron（默认 06:00 UTC = 14:00 北京时间；可按需调整）
- **Workflow**：`.github/workflows/daily-case-harvest.yml`
  - 检出仓库 → 安装依赖 → 运行采集脚本（--max 10）→ git 提交 cases.ts 变更 → 推送回仓库
- **Secrets 依赖**：搜索 API / LLM API Key 等以 GitHub Secrets 注入，不落库
- **沉默死亡追踪**：由 `ENABLE_STALE_TRACKER=1` 开启（默认开）。workflow 会先 `apt-get install dnsutils` 装 `dig`——没有 dig 时 NXDOMAIN 判定会退化为标准库重试，准确率下降但不会误判
- **已产出域名台账**：`scripts/stale_seen.json` 记录已经产出过的域名，每天重扫同一月份时不重复喂给 LLM。随 cases.ts 一起提交
- **失败处理**：workflow 失败不阻塞；自动重试 1 次；连续失败 3 天触发通知主 Agent
- **产物**：每次运行生成 `codeact/output/opc_cases_YYYYMMDD.md`（新增清单 + 来源 + 累计数）
