# 一人公司坟场 · 案例库更新机制与内容方案

> 目标：让案例库成为可持续运营的内容资产——每周有新增、每条可溯源、死因可拆解、教训可复用。

---

## 一、收录标准（什么案例值得进坟场）

一条案例必须同时满足以下 **5 条硬门槛**，缺一不可：

| # | 门槛 | 说明 |
|---|------|------|
| 1 | **真实发生** | 有公开报道、官方公告、创始人自述或可靠二手来源，不接受编造、推测、合成案例 |
| 2 | **可溯源** | 至少 1 个可点击核验的来源链接（媒体文章 / 官网公告 / 创始人帖子 / 访谈） |
| 3 | **死因可拆解** | 能拆出"表层原因 → 中间机制 → 深层机制"三层，且能归入六大死因之一 |
| 4 | **AI / OPC 属性** | 创始人是独立开发者 / 一人公司 / 极小团队（≤5 人），且失败与 AI 应用或 AI 冲击直接相关 |
| 5 | **有教训价值** | 读者能从中提炼出可执行避坑清单（至少 3 条），而非单纯猎奇 |

**优先收录**：死因覆盖度低的分类、中国本土案例、近 12 个月关停的案例。
**暂不收录**：大厂砍产品线（属战略收缩而非创业失败）、纯融资暴雷但无产品故事的、合成/化名案例。

## 二、死因分类体系（复用六大类，主因 + 子因）

```
死因（主因，单选）         子因（自由填，1-2 个短语）
─────────────────────────────────────────────
获客失败                  个人品牌未建立 / 渠道缺失 / 流量成本失控
需求验证缺失              先做再想 / 伪需求 / 市场被替代
商业模式脆弱              融资来源单一 / 大客户依赖 / 用户多不赚钱 / 回款风险
成本结构失衡              固定支出吞噬 / 算力成本失控 / 库存积压 / 毛利为负
同质化竞争                AI 抹平门槛 / 被通用模型吸收 / 价格战
合规与决策风险            监管处罚 / 数据合规 / 造假曝光 / 一人决策无纠偏
```

- 一条案例只能选 **1 个主因**（用于统计与榜单），子因可写多个。
- 主因选择规则：按"**最先导致死亡的那一环**"归因，而非最显眼的一环。

## 三、来源渠道清单（每周巡检）

### 中文渠道（重点，中国本土案例优先）
- 36氪（创业失败复盘专栏、AI 应用观察）
- 澎湃新闻（一人公司/OPC 专题报道）
- DoNews / 虎嗅（创业者实录）
- 人人都是产品经理（产品经理复盘）
- 微信公众号 OPC / 独立开发者社群（SoloNest 等）
- 知乎 / 即刻（创始人亲述关停）

### 海外渠道
- Failory Newsletter（倒闭访谈，当前案例库主要来源）
- AI Graveyard / Vibe Coding Graveyard（AI 工具关停档案，注意区分真实名与化名）
- Indie Hackers（独立开发者失败帖）
- Hacker News（关停公告帖 + 复盘讨论）
- TechCrunch / The Information（融资后关停新闻）

**巡检节奏**：每周 1 次集中巡检（30-60 分钟），滚动 4 个来源；重大关停事件（如头部 AI 工具关停）即时收录。

## 四、收录流程（五步流水线）

```
发现 → 初筛 → 核实 → 撰写 → 评审发布
```

| 步骤 | 动作 | 输出 | 负责 |
|------|------|------|------|
| 发现 | 巡检来源渠道，收集候选案例 | 候选清单（每周 5-10 条） | Agent |
| 初筛 | 对照 5 条硬门槛快速过滤 | 通过清单（2-4 条） | Agent |
| 核实 | 打开来源链接，核对时间线/金额/死因/创始人背景；多条来源交叉验证 | 事实卡（字段齐全） | Agent |
| 撰写 | 按模板补全叙事字段（墓碑摘要/动机/时间线/三层拆解/教训） | 完整案例 JSON | Agent |
| 评审发布 | 跑 `pnpm validate` + 浏览器预览，确认无报错后合入 | 上线案例 | Agent |

**质量红线**：
- 金额、时间、人名必须来自来源原文，不得推测；来源冲突时以多源一致为准，仍冲突则不收录该细节。
- `verified: true` 仅当至少 2 个独立来源或 1 个权威来源（官方公告/主流媒体）可核验；只有单方自述（创始人帖子）标 `false`。
- 每条案例撰写前必须打开来源页面，禁止凭搜索摘要直接写。

## 五、内容模板（每条案例必填字段）

沿用 `src/data/cases.ts` 的 `CaseRecord` 结构：

| 字段 | 要求 |
|------|------|
| slug | 小写英文短横线，语义化且唯一 |
| name | 墓碑名：产品名或"行业+失败形态"描述名（匿名案例） |
| status | dead / acquired / pivoted 三选一 |
| founderBg / region / industry | 创始人背景、地区、行业 |
| startedAt / closedAt / lifespanMonths | 起止年份、存活月数（精确到可核验粒度） |
| investment / fundingType | 投入金额 + 自筹/融资/混合 |
| deadCause / deadCauseSub | 主因 + 子因 |
| source | 来源（媒体名 + 可选文章标题） |
| verified | 是否双源/权威核验 |
| epitaph | 墓碑摘要：3 行内，点出死因与关键数字，有冲击力 |
| motivation | 创业动机：1 段（100-200 字） |
| timeline | 3-6 个关键节点（time + event） |
| breakdown | ≥3 层：表层原因 → 中间机制 → 深层机制 |
| lessons | 3-5 条可执行避坑清单 |

## 六、更新节奏

| 周期 | 动作 |
|------|------|
| 每周 | 巡检来源 + 收录 1-2 条新案例（优先补死因覆盖缺口） |
| 每月 | 批量补录 3-5 条 + 死因分布复核 + 首页榜单重排 |
| 季度 | 案例库健康度报告：死因覆盖、地区分布、行业分布、验证率 |

初始阶段（前 4 周）：每周新增 2-3 条，快速把案例库从 10 条拉到 20+ 条，让六大死因全覆盖、首页榜单有新鲜感。

---

## 七、去重与追踪

- **slug 唯一**：新增前检查 `CASES` 中不存在同名/同产品案例；同一产品只收录一次，后续变化用状态迁移（dead → pivoted）而不是新开一条。
- **同源不重复收录**：同一事件的多个媒体报道只收录 1 条，source 合并列多个媒体。
- **已收录名单**：维护"已收录产品清单"（名称+slug），避免轮换关键词时重复收录。
- **死因覆盖均衡**：每次新增优先选择当前覆盖最少的主因分类，保证六大类统计不畸形。

---

## 八、运营联动

1. **首页"最新下葬"榜单**：按 `closedAt` 倒序自动取最新 5 条，新增即上榜单。
2. **死因分布**：首页统计条自动随 `CASES` 更新，无需手改。
3. **筛选器**：行业 / 死因 / 地区自动从数据生成，新增案例自动进入筛选范围。
4. **SEO**：详情页 `<title>` 已含案例名 + 死因 + 品牌，新案例自动继承。
5. **投稿入口**：`/contribute` 页收集读者案例线索，收录时优先处理投稿线索并回访。

---

## 九、数据模型扩展建议（后续迭代）

当前 `CaseRecord` 满足 MVP。达到 30+ 条后可扩展：
- `tags[]`：产品类型、AI 能力类型、失败模式标签，支撑更细筛选
- `metrics`：可核验的收入/用户/融资数据快照（供对标）
- `related[]`：关联案例 slug（同死因/同行业互链）
- `revenueFailed` / `causeChain`：因果链字段，供"死因图谱"可视化
- 投稿线索表：`/contribute` 提交内容 → 结构化线索 → 待核实队列
